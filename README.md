# HA Cards

Home Assistant Lovelace cards that look like the equipment they represent —
a power meter that reads like a power meter, a controller that reads like the
controller on the wall.

Built alongside four building-systems bridges
([Niagara](https://github.com/rellis-erigon/Niagara--HA),
[Daikin D-BACS](https://github.com/rellis-erigon/HA-Daikin-DBACS),
[Crestron](https://github.com/rellis-erigon/Crestron-CIP-HA),
[Q-SYS](https://github.com/rellis-erigon/QSYS-QRC-HA)), but none of them is
required: every card works with any entities you point it at, and each
bridge-specific feature switches itself off when that bridge is absent.

See [PLAN.md](PLAN.md) for the full design and roadmap.

## Adding a card the ordinary way

Add card → search for it → fill in the fields. Every card has a visual
editor with a **field per point**, so nothing has to be written by hand:

- **Title** — the nameplate along the top of the card. Left blank, it
  falls back to the name of the device in **Device** below, so a card
  pointed at a device is never anonymous.
- **Faceplate** — which graphic, with the model it emulates listed.
- **Device** — set this and every point below is matched from that
  device's entities. Takes the device id or its name.
- **Options** — number of pumps, zones, units, and so on, where the
  faceplate is parametric. The point list changes to match.
- **Hide controls with nothing bound** — on by default. A faceplate
  declares everything the equipment could have; this leaves out what you
  have not wired, and the card footer says how many it hid. Turn it off
  to see the full panel with dead controls dark.
- **One field per role** — `Volts l1`, `Pump1 speed`, `Zone3 mute`.

The editor uses Home Assistant's own entity picker where it is available
and falls back to a plain field with entity-id completion otherwise, so
it is never blank.

## Letting a bridge build the card for you

The Niagara, Q-SYS and Crestron bridges each generate a card for what they
have discovered, so the entity ids never have to be typed out:

| Bridge | How | What you get |
|--------|-----|--------------|
| Niagara BMS | Type a device against a template | The faceplate card plus a list of whatever the faceplate does not draw. The face is picked per device, because a template matches equipment of every make. |
| Q-SYS | `qsys_bridge.generate_zone_card` | One rack carrying every exposed zone, each strip labelled with the device's own name. |
| Crestron | `crestron_cip.generate_room_card` | A room assembled by matching join names to roles — returned with its working, because it is a guess. |

Each returns the card and its YAML, so you can paste it or check it first.

## Dashboards that build themselves

Two view strategies turn what the bridges have discovered into pages, and
re-run on every load, so moving a device to another area in Home Assistant
moves it on the next refresh:

```yaml
strategy:
  type: custom:site-floors        # floors → areas → equipment, cameras, the rest
```

```yaml
views:
  - strategy:
      type: custom:bridge-devices # every generated card, grouped by area
      area: plant_room            # optional
```

An area page of `site-floors` can be given `rooms`, which lays each room's
equipment out in room-number order, three to a row, dropping to two or one
as the screen narrows. A suite's units (`Room 101 Bed …`, `Room 101 Living …`)
share one cell, and a room listed with nothing in it shows its number:

```yaml
rooms:
  - [104, 103]
  - [105, 101]
  - [null, 151]
```

## Daikin AC units

With the [D-BACS bridge](https://github.com/rellis-erigon/HA-Daikin-DBACS)
installed, `hvac-controller-card` also shows:

- **The unit's model and rated kW** (cooling and heating) under its name,
  read from the climate entity's `model`, `rated_cooling_kw` and
  `rated_heating_kw` attributes.
- **Whether a change took.** A change shows as sending, held (the bridge
  spaces writes to one point), waiting, then confirmed or failed with the
  reason, from the entity's `pending_changes` and `last_change`. A unit
  that never reports the new value is shown as not confirmed after five
  minutes rather than left looking done.

The generated pages put `ac-history-card` and `ac-mapping-card` under each
unit. Without the bridge these attributes are simply absent and the card
draws as before.

## Installing

Add this repository to HACS as a **Dashboard** repository, install, then add
a resource for **only the cards you use**:

```
/hacsfiles/HA-rellis-erigon-Cards/bms-meter-card.js      (JavaScript Module)
```

or `all-cards.js` if you would rather add one resource and be done.

## Using the meter card

```yaml
type: custom:bms-meter-card
faceplate: schneider-pm2200
name: DB-L3-KE Power
entities:
  energy_total: sensor.db_l3_ke_power_metertotal
  power_total: sensor.db_l3_ke_power_3phase_active_power
  volts_l1: sensor.db_l3_ke_power_phase_1_v
  # ...
```

Roles left out are matched from the entity ids where the naming is
recognisable, so on a typed Niagara device the `entities:` block is usually
unnecessary. **A role with nothing bound renders as an unlit display rather
than disappearing** — an unlit segment is honest; a hidden one makes a
half-configured card look complete. An entity that is unavailable reads
differently again, because a confident number from a dead point is the one
outcome worth designing against.

## Using the XPanel card

`crestron-xpanel-card` needs the
[Crestron CIP integration](https://github.com/rellis-erigon/Crestron-CIP-HA)
(0.22 or later) and Ruffle, served from `/local/ruffle/0.7.1/ruffle.js`.

1. Give the processor its room panels: **Settings → Devices & services →
   Crestron CIP → (processor) → Configure → Add or replace a room's
   panel**: the room, its IPID, and the panel's `.zip` (picked from a
   drop-down of the files on Home Assistant, or uploaded).
2. **Add card → Crestron XPanel Card**, and pick the room's panel device.

```yaml
type: custom:crestron-xpanel-card
device: Room 1 panel
scale: 0.75
background: true
```

| Option | Default | Does |
|--------|---------|------|
| `device` | — | The room panel's device; a processor's own device shows its first panel |
| `scale` | `1` | 0.1–1, a fraction of the size that fits the window |
| `fit_window` | `true` | Fit the window's width and height; `false` fills the card's width |
| `background` | `false` | Start the panel when Home Assistant opens, on any dashboard, so it is loaded before its view is shown |
| `title` | — | A heading above the panel |
| `xpanel_url` | the room's panel | Another `container.swf` to run |
| `debug` | `false` | Copy Ruffle's console into Home Assistant's log |

The panel runs once per browser tab and keeps running while you change
views or hide the window; every browser and user sees the same state,
served from one connection per room. The integration's README covers how,
and what to check when a panel will not start.

## One vocabulary, every bridge

The same equipment reaches Home Assistant by more than one road. A Daikin
fan coil arrives as BACnet objects through a
[D-BACS gateway](https://github.com/rellis-erigon/HA-Daikin-DBACS), as oBIX
points through [Niagara](https://github.com/rellis-erigon/Niagara--HA), and
sometimes as joins through a Crestron processor — and the entity ids look
nothing alike:

```
sensor.dbacs_1_1_00_room_temperature     # named for people
sensor.fcu_12_roomtemp            # Daikin's own object name, untouched
sensor.room_12_space_temperature         # a third-party BMS point
```

**All three bind to `room_temp`.** A role is named for what a point *means*,
and every spelling the bridges produce is listed against that one name, so a
card needs only:

```yaml
type: custom:hvac-controller-card
faceplate: fcu-unit
device: Unit 12
```

No `entities:` block, no per-integration mapping. The HVAC roles are:

| | |
|---|---|
| **Core** | `run` `fault` `fault_code` `hvac_mode` `hvac_action` `room_temp` `setpoint` `fan_speed` `swing` |
| **Status** | `filter` `compressor` `heater` `fan_running` `comms` `energy_saving` `thermo_off` `forced_off` |
| **Setpoints** | `setpoint_adjust` `setpoint_cool` `setpoint_heat` `humidity_setpoint` |
| **Air handling** | `supply_air_temp` `return_air_temp` `outside_air_temp` `humidity` `co2` `valve_position` `damper_position` `filter_dp` `occupancy` |

Two distinctions in there are worth knowing, because getting either wrong
shows a plausible wrong number rather than nothing:

- **`fan_speed` is how fast, `fan_running` is whether.** A Daikin gateway
  publishes both and they disagree constantly — a unit can report airflow
  "High" with the indoor fan stopped.
- **`setpoint` is absolute, `setpoint_adjust` is an offset.** Some
  controllers call a ±3 K dial "TempAdjust" and some call the room setpoint
  the same thing. `setpoint` deliberately refuses to match
  `cooling_setpoint` or `heating_setpoint` for the same reason: binding one
  of those as *the* setpoint shows a room being held where it is not.

`scripts/test-role-binding.mjs` checks every bridge's spelling against the
role it means, **and against nothing else** — anything matching two roles
fails. A loose pattern is the most repeated bug in this workspace, because
the card still renders; it just lies.

## Faceplates that build themselves

Most faceplates are fixed artwork. Some are not: a pump set is the same
equipment at different widths, so `vertical-pumpset` declares an option and
builds its skid, manifold and roles from it.

```yaml
type: custom:pump-system-card
faceplate: vertical-pumpset
options:
  pumps: 6
```

Roles follow the count — `pump1_run` through `pump6_run`, and the same for
`_speed` and `_fault` — alongside `system_pressure`, `pressure_setpoint` and
`common_fault`. They match the Niagara pump-set template's slot names, so a
device typed there resolves without a role map.

## Adding a faceplate

A faceplate is data. See `src/faceplates/meter/generic3phase.ts` for the
smallest complete example: artwork, a size, and a list of regions that each
name a *role* rather than an entity.

Requests for new models are welcome — open an issue with the manufacturer and
model, a straight-on photograph, and the manual or datasheet if you have it.
Without a photograph taken square-on it cannot really be done.

## If a change does not appear

Home Assistant's frontend is a progressive web app with a service worker, so
a plain reload — and often a hard reload — will serve the cached bundle. A
query string on the resource URL is not always enough either.

What reliably works is deploying to a path that has never been fetched:

```
/local/ha-cards/<build>/bms-meter-card.js
```

Keep the build stamp in the directory name and update the resource to match.
The browser cannot have a stale copy of a URL it has never seen.

## Rebuilding the sample dashboard

Two scripts, run inside the add-on container (they authenticate with
`SUPERVISOR_TOKEN` and need the `websockets` package):

```
python3 scripts/build-samples.py          # every faceplate, bound to live points
python3 scripts/build-generated-view.py   # the cards the bridges generate
```

`build-samples.py` also writes `samples/dashboard.yaml`. That file is
published, so it is sanitised first: entity ids are replaced by neutral
ones named after the role they fill, and strip labels by their index.
Pass `--no-export` to update the dashboard without rewriting it.

`build-generated-view.py` is never exported — every title and label in
it is a real device name.

## Development

```bash
npm install
npm run build          # rollup + faceplate catalogue
npm run check          # typecheck only
```

If the native Rollup binary cannot load in your environment, build with the
WASM build instead:

```bash
node node_modules/@rollup/wasm-node/dist/bin/rollup -c
```

Before committing:

```bash
npm test                                  # contract, binding, layout, strategy and control tests
python3 scripts/check-no-site-detail.py   # no real addresses, rooms or site names
```

The tests load `dist/`, so build first. `npm run contract:update` accepts a
deliberate faceplate or role change into `faceplates/roles.lock.json`.
